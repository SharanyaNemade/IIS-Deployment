###### **If your SQL Server and IIS are on the same Windows machine, then you may not need to change the connection string at all.**

##### **In my appsettings.json i have this connection string:-**

"ConnectionStrings": {

"DbConn": "Server=localhost\SQLEXPRESS;Database=Dapper;Trusted_Connection=True;TrustServerCertificate=True;"

}

what changes need to do?

If your SQL Server and IIS are on the same Windows machine, then you may not need to change the connection string at all.

Your current connection string is:

"ConnectionStrings": {

"DbConn": "Server=localhost\SQLEXPRESS;Database=Dapper;Trusted_Connection=True;TrustServerCertificate=True;"

}

The important part is:

Server=localhost\SQLEXPRESS

When your application runs under IIS, localhost means the IIS server itself.







##### **Scenario 1 — SQL Server is on the same machine as IIS**

For example:

Your PC

│

├── IIS

│    └── Employee Management API

│

└── SQL Server Express

```
 └── Dapper database 
```

Then you can keep the connection string as it is:

"ConnectionStrings": {

"DbConn": "Server=localhost\SQLEXPRESS;Database=Dapper;Trusted_Connection=True;TrustServerCertificate=True;"

}

However, there is one important issue: Trusted_Connection=True uses Windows Authentication.

Your application is no longer running directly as your Windows user.

It will run under an IIS Application Pool identity.

For Example:-

Your Windows account

```
  ↓ 
```

Visual Studio

```
  ↓ 
```

SQL Server

```
  ↓ 
```

Works

But under IIS:-

IIS

↓

EmployeeManagementPool

↓

ASP.NET Core

↓

SQL Server

SQL Server needs to allow that IIS identity to access the Dapper database.

Recommended approach for your local IIS setup

If SQL Server Express and IIS are on the same machine, you can configure SQL Server permissions for the IIS Application Pool identity.

Suppose your Application Pool is:

EmployeeManagementPool

The Windows account you can grant access to is:

IIS APPPOOL\EmployeeManagementPool

In SQL Server Management Studio:

Security

↓

Logins

↓

New Login

Enter: `IIS APPPOOL\EmployeeManagementPool`

Then map it to: Dapper

and give it the database permissions your application requires.

For example, if this is your development/test server and the application needs CRUD access, you would grant appropriate database roles/permissions rather than changing the application to use an administrator account.

But Windows authentication across machines introduces additional configuration, so for a real server environment you would normally design the SQL authentication/service-account setup properly rather than simply putting credentials into appsettings.json.

One important check before you do this

If you cannot find:

IIS APPPOOL\EmployeeManagementPool



in the New Login dialog, don't panic. This is a common point of confusion.


You can click Search... next to Login name and then enter the application pool identity, or we can create it using a SQL command.

In fact, for IIS application pool identities, I generally prefer using the exact identity:


CREATE LOGIN [IIS APPPOOL\EmployeeManagementPool] FROM WINDOWS;

and then map it to your Dapper database.
